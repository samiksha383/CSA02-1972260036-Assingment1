# TASK 1 – Understand the Problem and Identify the Data

## 1. Problem Overview
The Grama Jyothi Rural Electricity Co-operative needs a reliable C billing system to replace an error-prone spreadsheet. The spreadsheet currently suffers from floating-point rounding discrepancies, negative unit calculations when 16-bit meters roll over past `65535`, and inconsistent tariff updates. The solution must scale from 1 village (4,000 houses) to 1 taluk (60,000 houses) and 1 district (800,000 houses) while guaranteeing accuracy to the exact paisa.

---

## 2. Identification and Justification of Data Items

### A. Inputs (Read per Household)
* **`house_id` (Household Number):** Uniquely identifies each consumer account across the co-operative (ranging from `1` up to `800,000` at district scale).
* **`category` (Consumer Category):** Identifies the tariff class (e.g., `'D'` for Domestic or `'C'` for Commercial), as different consumer categories may carry different fixed charges or slab rates.
* **`prev_reading` (Previous Meter Reading):** The 16-bit unsigned counter value recorded at the end of the prior billing cycle (`0` to `65535`).
* **`curr_reading` (Current Meter Reading):** The 16-bit unsigned counter value recorded at the end of the current billing cycle (`0` to `65535`).

### B. Computed Outputs (Generated per Household & Batch)
* **`units` (Units Consumed):** The non-negative electricity consumed in kilowatt-hours (kWh), calculated using modular 16-bit subtraction so rollovers from `65535` to `0` yield valid positive consumption.
* **`fixed_charge` (Fixed Monthly Charge):** The base monthly connection fee stored in integer **paise** (e.g., Rs 50.00 = `5000` paise).
* **`energy_charge` (Slab-Based Energy Charge):** The variable consumption cost computed across progressive tariff slabs, stored in integer **paise** to prevent binary floating-point rounding errors.
* **`total_bill` (Total Household Bill):** The exact sum `fixed_charge + energy_charge` in integer **paise**, formatted as `Rs X.YY` only during final output.
* **`grand_total` (Batch / District Total):** The cumulative sum of all `total_bill` values across up to 800,000 households, stored in a 64-bit integer to prevent arithmetic overflow.

### C. Constants (Unchanging During Program Execution)
* **`SLAB1_UNITS` (`100`):** Upper limit of the first consumption slab (0–100 units).
* **`SLAB2_UNITS` (`200`):** Upper limit of the second consumption slab (101–200 units).
* **`RATE1_PAISE` (`0`):** Tariff rate for Slab 1 (Rs 0.00 / free).
* **`RATE2_PAISE` (`225`):** Tariff rate for Slab 2 (Rs 2.25 per unit = 225 paise).
* **`RATE3_PAISE` (`450`):** Tariff rate for Slab 3 above 200 units (Rs 4.50 per unit = 450 paise).
* **`FIXED_CHARGE_PAISE` (`5000`):** Standard monthly fixed charge (Rs 50.00 = 5000 paise).
* **`METER_MODULUS` (`65536`):** The wrap-around capacity ($2^{16}$) of a 16-bit hardware meter register.

---

## 3. Data Characteristics (Negative, Fractional, or Very Large Values)
* **Negative Values:** No valid input or output in this domain can be negative. A negative reading indicates corrupted input data, and a negative bill indicates a rollover bug.
* **Fractional Values:** Tariff rates such as Rs 2.25 and Rs 4.50 contain two decimal places. Because binary floating-point types (`float`) cannot represent base-10 fractions like `0.05` or `2.25` exactly, all monetary values are scaled by `100` and stored as exact integers in **paise**.
* **Very Large Values:** While an individual monthly bill rarely exceeds Rs 10,000 (`1,000,000` paise), the **district-level total** across 800,000 households can reach $800,000 \times 1,000,000 = 8 \times 10^{11}$ paise (Rs 800 Crore). This exceeds the maximum capacity of a 32-bit signed integer ($2.14 \times 10^9$) and requires a 64-bit integer (`long long`).

---

## 4. Invariants and Validation Rules
Every valid bill generated by the system must satisfy five strict rules:
1. **Valid Meter Range:** $0 \le \text{prev\_reading} \le 65535$ and $0 \le \text{curr\_reading} \le 65535$.
2. **Non-Negative Consumption:** $0 \le \text{units} \le 65535$.
3. **Minimum Bill Floor:** $\text{total\_bill} \ge \text{fixed\_charge}$ (even when `units == 0`).
4. **Additive Consistency:** $\text{total\_bill} \equiv \text{fixed\_charge} + \text{energy\_charge}$ with zero rounding discrepancy.
5. **Monotonicity:** If $\text{units}_A > \text{units}_B$, then $\text{total\_bill}_A \ge \text{total\_bill}_B$.

---

## 5. Assumptions
1. **Single Rollover Limit:** No rural household consumes $65,536\text{ kWh}$ or more within a single 30-day billing period; therefore, at most one counter rollover occurs per cycle.
2. **Whole-Unit Meter Resolution:** The legacy electro-mechanical/digital meters report whole kilowatt-hours (kWh) as integers.
3. **Uniform Tariff Cycle:** Tariff rates remain constant for the duration of a single billing run and are revised only between billing cycles.

---

## 6. Alternative Concept and Complexity Analysis

### Alternative Approach: Storing Meter Readings as Text Strings
If meter readings were stored and processed as fixed-width character strings (e.g., `"01530"`, `"65400"`) instead of 16-bit integers:
* **Algorithmic Change:** Before computing consumption or detecting a rollover, each string of length $d$ digits would have to be validated character-by-character (`isdigit`) and converted into an integer using a loop (`val = val * 10 + (str[i] - '0')`) or `strtol()`. Comparing two readings lexicographically (`strcmp`) would also require scanning digit by digit from left to right.

```c
/* Pseudocode for String-Based Reading Conversion */
int parse_reading(const char *str, int d) {
    int value = 0;
    for (int i = 0; i < d; i++) {          // Runs d times per reading
        if (str[i] < '0' || str[i] > '9') return -1;
        value = value * 10 + (str[i] - '0');
    }
    return value;
}
```

### Complexity Comparison ($d$ = number of digits, $N$ = number of households)

| Metric | Integer Representation (`unsigned short`) | Text String Representation (`char[6]`) |
| :--- | :--- | :--- |
| **Conversion Time per Reading** | **$O(1)$** (Already in binary hardware format) | **$O(d)$** (Must scan and multiply all $d$ characters) |
| **Comparison / Subtraction Time** | **$O(1)$** (Single CPU `SUB`/`CMP` instruction) | **$O(d)$** (Lexicographical scan or post-conversion math) |
| **Batch Time for $N$ Houses** | **$O(N)$** with minimal constant factor | **$O(N \cdot d)$** (Up to $5\times$ more loop iterations for 5 digits) |
| **Space per Reading** | **2 bytes** (`sizeof(unsigned short) == 2`) | **6 bytes** (`5` ASCII digits + `1` null terminator `'\0'`) |
| **District Memory ($800,000 \times 2$ readings)** | **3.2 MB** | **9.6 MB** ($3\times$ memory overhead) |

**Conclusion:** Integer representation reduces memory usage by **66.7%** and eliminates $O(d)$ parsing overhead on every reading.
